# WEB07｜双阶段图墙与单屏异步队列

日期：2026-08-20
阶段负责人：🦁 辛巴
实现：🐾 丁满
验收：🐦 沙祖

## 目标

在不注册、可同时提交多个 GPX 的前提下，把输入、参数、两阶段图片、全局匿名队列、
本浏览器任务和 5+1 输出集中到一个桌面屏幕。刷新页面后，任务由浏览器匿名身份恢复，
而不是依赖当前页面内存。

## 方法

1. 图像证据拆为两个常驻阶段，不复用同一个画廊：
   - 阶段 A：Blender 工程仿真，当前基线 `N=3`（装配、顶视、侧视）；
   - 阶段 B：最终交付核验，当前基线 `M=3`（最终装配、最终顶视、最终侧视）。
2. 未产生图片时也渲染全部 `N+M` 个占位；阶段完成后仅替换对应阶段图位。
3. 最终任务恢复时，从同一任务目录恢复阶段 A 三张工程图，并以最终 manifest 填充阶段 B，
   保留前后证据链。
4. 队列接口增加匿名 `stage_counts`；公开 Worker 数、运行数、等待数和阶段分布，
   只向匿名设备本人显示自己的路线名称与任务详情。
5. 桌面端使用三栏网格：左侧输入与参数、中间两阶段图墙、右侧队列与交付；
   旧分步样式中的 `order` 不再参与排版，各区显式绑定网格行。

## 事实与验证

- 改造前 1440×900 浏览器页面文档高度为 2156 px，只有一套 3 图画廊。
- 改造后 1440×900：页面尺寸与视口均为 `1440×900`，无页面级滚动；三栏宽度为
  `320 / 724 / 340 px`。
- 初始态阶段 A 有 3 个占位，阶段 B 有 3 个占位，共 6 个；队列阶段显示 7 个阶段标签。
- 最新完成任务
  `WEB_20260820_170951_681221_2025-02-23_从化星溪线` 的工程三机位与最终三机位
  共 6 个 PNG 均存在且非空；抽查工程图和最终图 HTTP 返回均为 `200 image/png`。
- `/api/queue` 返回 `worker_capacity / running_count / queued_count / stage_counts`；空闲态实测
  为 1 Worker、0 运行、0 等待、空阶段分布。
- Python 编译、前端 JavaScript 解析和 `git diff --check` 均通过。
- 4173 前端与 4174 后端重启后均为 RUNNING。

## 假设与边界

- 当前生产流程固定生成三机位，所以初版 `N=3、M=3`；渲染函数允许结果图片数超过三个，
  图位数量可在后续按任务类型扩展。
- 桌面宽度不低于 1180 px 时坚持单屏；窄屏改为两栏或单栏滚动，不以缩小到不可读为代价。
- 全局队列只显示聚合数量和阶段，不显示其他客户的文件名、标题、预览或下载地址。
- 本轮未重新运行耗时的 Blender 生产任务；使用最新已完成的同源任务验证六张图片资产，
  并对新的显示逻辑、接口、布局和服务状态做回归。

## 结论

WEB07 已满足“两个阶段的 N+M 图位始终存在、按阶段原位更新、匿名多用户队列透明、
桌面一屏展示”的阶段目标。后续新增机位时，只需扩充阶段槽位配置和生成结果数组，
不应重新设计页面结构。

## 下一步

## WEB07.1｜流程语义与超宽屏修正

用户验收指出，原版虽然保留了六个图位，但仍有两个问题：超宽屏受 `1600 px` 最大宽度
限制而浪费两侧空间；A、B 两排空框没有解释先后关系和检查目的。

修正后的产品定义：

- **阶段 A／工程仿真**：先生成。使用本次 GPX 的真实地形、轨迹与水系几何，检查整体装配、
  顶视冲突和侧视高度；此时底座是参考体，尚未承诺最终文字、Logo、3MF 容器和 Bambu QA。
- **阶段 B／交付核验**：A 通过后生成。来自最终交付 Blender，包含最终底座文字、Logo、
  四件装配关系；随后检查 5 个 3MF、颜色、对象层级、Z 范围和打包清单，决定是否可下载打印。

界面修正：

- 移除工作区最大宽度，三栏在超宽屏占满可用空间；大于等于 1800 px 时 A/B 并排，
  普通桌面上下排列，保持清晰的 `A → B` 依赖。
- 六个预留位不再是空框：每格显示 `A1–A3 / B1–B3`、机位名称、检查目的和当前状态。
- 空位状态随 `解析 GPX → 生成地形水系 → 渲染三机位 → 最终建模 → Bambu QA → 下载`
  原位更新，使客户无需猜测后台正在做什么。
- 每个图位固定为 `16:9`，使用六边形构图提示；真实图片使用 `object-fit: contain`，不裁掉
  底座文字或六边形边缘。
- 真实图片使用放大镜交互，点击后以不超过 `92vw × 78vh` 的对话框显示原图，并保留机位目的。

浏览器验收：`1280×720` 下工作区使用 `1244 px` 可用宽度（左右仅各 18 px 页面边距），
文档高度等于视口高度；六个预留位均为 `1.78` 长宽比，输入、参数、创意、A/B 图位、队列、
输出和操作按钮均在一屏内可见。

## WEB07.2｜消除等高空腔

WEB07.1 在超宽屏把 A、B 阶段并排，但阶段容器被拉满整列高度、内部图片仍固定为
`16:9`，导致每排图片只有约 `418 × 74 px`，其下出现大面积无意义空腔。左右栏也使用
弹性等高行，内容少时白色卡片被拉长。

修正方法：

- A、B 在所有桌面宽度均上下排列，各自占据图墙的一半，明确表达先后关系；
- 三机位图片行改为填满阶段剩余高度，使用 `object-fit: contain` 保持六边形模型完整；
- 左右辅助栏改为内容驱动高度，取消参数、创意、队列和输出卡片的强制拉伸；
- 收窄左右辅助栏，把新增宽度让给中间图片证据；
- 在高度不超过 `780 px` 的桌面缩短 GPX 草模条，优先保证六张核验图的可读面积。

宽屏浏览器验收（`2048 × 1120`）：A、B 各 `1288 × 338 px`，六个图位均约
`418 × 285 px`，长宽比 `1.47`；页面尺寸与视口一致，无页面级滚动。最小桌面验收
（`1280 × 720`）：六个图位约 `206 × 109 px`，长宽比 `1.89`，文档高度仍等于视口。
因此图位在两种桌面尺寸都保持适合六边形模型的接近 `3:2–16:9` 画幅，不再是窄条占位。

## WEB07.3｜消除任务状态的假失败

用户提交 `WEB_20260820_183345_132179_2026-08-07-14-53-55-六片山2km` 后，页面短暂显示
“仿真失败”，但 Worker 仍在继续生成。核验确认 TrailPrint3D、Blender 三机位、最终 5+1、
ZIP 和 QA 全部成功，任务最终状态为 `FINAL_READY / QA_PASS`。

根因是任务元数据的并发读写竞争：Worker 直接覆写 `job.json` 时存在极短的截断窗口；
前端恰好轮询到该窗口，后端无法解析 JSON，按“任务不存在”返回一次 404；前端又把单次
404 当成终态错误，造成页面假失败。

修正与门禁：

- `configure_route_scene.py` 对 `job.json` 和 `route_profile.json` 使用同目录临时文件加
  `Path.replace()` 的原子写入；
- 前端读取新提交任务时，对短暂 404 做最多 6 次、逐步延长的有限重试；持续失败仍正常报错，
  不掩盖真实的任务不存在或权限问题；
- 新增 `test_job_metadata_atomic.py`，在 1000 次写入期间持续并发解析，任何半截 JSON 都使
  测试失败；
- 服务重启后实测任务接口返回 `FINAL_READY / complete / 100 / QA_PASS`，六个成果文件与
  完整 ZIP 均有下载记录。

结论：一次瞬态状态读取失败不得覆盖 Worker 的持久状态。页面失败提示必须能与任务状态文件、
后台日志和最终 QA 三者之一形成可追溯证据。

## WEB07.4｜左侧参数栏防裁切

用户验收发现，低高度桌面在任务内容变长时，左侧参数栏可能被固定网格行高与单屏外壳共同
裁切。修正低高度桌面的控制栏策略：四张卡片改为内容自适应行高；只有内容确实超过可用高度
时，左栏自身启用细滚动条，中间六张图和右侧队列保持原位。

浏览器回归：

- `1280 × 720`：输入、真机参数、标题元素、真机基线四块全部可见，各卡片
  `clientHeight == scrollHeight`，无内部裁切；
- `1440 × 900`：文档与视口均为 `1440 × 900`，左栏无需滚动且全部内容可见；
- 页面加载 `dashboard.css?v=20260820-7`，避免旧缓存继续显示裁切版本。

## WEB07.5｜参数栏与地形厚度策略

- 两列参数改用可收缩网格，滑杆、标题、日期和元素开关均不得撑破左侧卡片。
- Web 新任务启用 TrailPrint3D 固定高程范围，并把地形总厚度限制为模型尺寸的 15%；超限时自动降低有效倍率。
- 高程倍率范围扩展为 `0.3–3.0`；工程摘要回显请求倍率、有效倍率、实际厚度和上限。
- 六片山 2 km 临时副本验证：100 mm、R8、高程 1.0，实际厚度 `12.884 mm ≤ 15.0 mm`；此前约 `23.032 mm`。
- 旧任务与原始 GPX 均不修改。Python/JavaScript 语法、3 项策略测试和 TrailPrint3D 真实生成均通过。

## WEB07.6｜客户文案与路线概览

- 空白态标题由内部占位语“未命名徒步”改为行动提示“上传 GPX，开始制作”。

- 队列仍保留排队位次、运行数和等待数，但改用“制作通道、后台制作”等客户语言。
