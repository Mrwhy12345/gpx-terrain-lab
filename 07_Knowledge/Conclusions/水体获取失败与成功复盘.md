# 水体获取失败与成功复盘

日期：2026-07-28  
案例：S02 星溪线

## 结论

今天的水体流程成功，不是因为数据源突然变好，而是因为把原先混在一起的四类问题
拆开处理，并将成功获取的原始数据持久化：

1. Overpass 数据获取；
2. OSM 标签覆盖；
3. 高德坐标显示；
4. 模型边界裁剪与打印筛选。

今天的空间核验主要读取已经保存在
`06_Experiment/S02_ColorTest/data/osm_probe/` 的原始 JSON 和 GeoJSON，没有
重新依赖实时 Overpass 请求。

## 以前为什么失败

### 1. 旧脚本依赖缺失

旧脚本 `query_osm_water.py` 使用第三方 `requests`，但当时运行脚本的系统 Python
没有安装该模块，直接出现：

`ModuleNotFoundError: No module named 'requests'`

这是本地运行环境失败，不是“星溪线没有水体”。

### 2. 查询标签过窄

旧查询只有：

`way["waterway"]`

因此会漏掉：

- `natural=water`；
- `water=pond`；
- `water=river`；
- `landuse=reservoir`；
- relation/multipolygon。

即使请求成功，也只能看到部分线状水体，容易误判为数据稀少。

### 3. 没有正向对照

只查询星溪线时，返回空或失败无法区分：

- Overpass 服务器不可用；
- 网络或依赖失败；
- 查询语句错误；
- 目标区域确实没有数据。

后来的 probe 先查询广州珠江这个已知有水的对照区，再查询星溪线，因此能够明确
证明接口可用，并判断目标区是否有覆盖。

### 4. 高德失败被误认为“水体失败”

高德页面最初把 878 个 GPX 点和水体几何大量送入 `AMap.convertFrom`，触发：

`10021 / CUQPS_HAS_EXCEEDED_THE_LIMIT`

这是高德坐标转换接口的瞬时 QPS 超限，不是 OSM 获取失败，也不是总配额已经用完。
数据已经存在，只是无法稳定显示在卫星图上。

### 5. 获取、显示和建模没有分层

完整 OSM Way 可能跨出 GPX 查询框。以前看到图层超出范围时，容易怀疑坐标或数据
错误。实际上 Overpass 相交查询返回完整 Way 是正常现象，必须在后续按最终模型
边界裁切。

## 后来为什么成功

### 1. 去掉脆弱的运行依赖

新脚本 `probe_osm_water.py` 使用 Python 标准库 `urllib`，不再依赖未安装的
`requests`。

### 2. 扩大语义覆盖

新查询同时包含：

- `nwr["waterway"]`；
- `nwr["natural"="water"]`；
- `nwr["water"]`；
- `nwr["landuse"="reservoir"]`。

星溪线最终返回 25 个 OSM 元素，其中 24 个可直接转换为 6 条线和 18 个面。

### 3. 增加服务端容错

probe 设置了：

- 三个 Overpass 服务器；
- POST 请求；
- 45 秒 Overpass 查询超时；
- 60 秒网络超时；
- 明确 User-Agent；
- 失败后切换服务器并短暂等待。

单个公共节点不稳定不再等于整个任务失败。

### 4. 建立正向对照

广州珠江对照区返回 36 个元素，证明查询链路有效；星溪线随后返回 25 个元素，
证明当地确实存在 OSM 水体数据。

### 5. 成功结果立即落盘

成功后保存：

- Overpass 原始 JSON；
- 线状水体 GeoJSON；
- 面状水体 GeoJSON；
- 数据源报告。

后续距离计算、QGIS、Blender 和打印筛选都读取本地派生文件，不受实时 API 波动
影响。

### 6. 高德只负责显示核验

WGS 84 到 GCJ-02 改为浏览器本地批量转换，不再调用高德坐标转换接口。高德只
加载官方图层，避免 878 个轨迹点和水系坐标触发 QPS 限制。

### 7. 使用精确模型边界

水体先在 WGS 84/局部米制坐标中计算与 GPX 的关系，再使用从 TrailPrint3D
地形 Mesh 提取的真实边界裁切，最后才进入 Blender。数据获取、显示和可打印几何
不再互相替代。

## 事实与推断

### 已确认事实

- 旧脚本因缺少 `requests` 无法运行；
- 旧查询只覆盖 `way["waterway"]`；
- 新 probe 在广州珠江和星溪线均成功；
- 星溪线原始响应和 GeoJSON 已保存；
- 高德曾返回 QPS 超限错误；
- 改用本地坐标转换后页面成功加载；
- 今天的打印筛选读取本地 osm_probe 文件。

### 合理推断

- 早期“没有返回”的印象很可能由本地脚本失败、窄查询和显示失败共同造成；
- 公共 Overpass 节点的瞬时波动可能加剧失败，但现有记录不足以把它确定为唯一
  原因；
- 成功的主要原因是工作流的可诊断性和持久化，而非某个服务器今天更稳定。

## 对外系统必须继承的规则

1. 获取阶段必须有已知正向对照或健康检查；
2. 公共数据服务至少配置三个端点和重试；
3. 原始响应成功后立即不可变落盘；
4. 获取、显示、核验、裁切和建模使用独立状态；
5. 空结果不能直接解释为“当地没有数据”；
6. 每个失败必须归类为依赖、网络、服务、查询、坐标、几何或打印；
7. 高德只作在线人工核验，不作 OSM/DEM 的替代数据源；
8. 后续流水线必须支持从本地 checkpoint 恢复，不重复请求成功的数据。
